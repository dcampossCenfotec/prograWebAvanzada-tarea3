4. Descripción de la actividad 
Contexto: 
La Tarea 3 cierra el bloque de React y abre el bloque de .NET. Integra los laboratorios 
guiados del Maratón de series (componentes, estado, formularios, consumo del API, 
React Router) y los contenidos de la semana 11: SQL Server, modelo relacional y 
Entity Framework Core. 
La tarea tiene dos partes. La Parte A reúne en un repositorio personal todos los 
laboratorios guiados realizados en el curso, funcionando. La Parte B es el diseño del 
servidor .NET de la entrega final del proyecto: el dominio del Innovation Hub, 
modelado en documentos durante el Avance 2, se diseña ahora en tablas de SQL 
Server para implementarlo después con Entity Framework Core. 
El alcance está acotado a propósito. La Parte B es de diseño: no se programa en C# 
ni hace falta instalar SQL Server. Se entregan documentos: el diagrama de la base 
de datos, la descripción de cada tabla, datos de prueba, consultas SQL escritas y el 
diseño de dos rutas de lectura. En la entrega final, ese diseño se convierte en código 
con Entity Framework Core.

2. Parte B — Diseño de la base de datos del Innovation Hub (repositorio 
del proyecto) 
La Parte B se hace en equipo, en la carpeta docs del repositorio del proyecto. Es un 
trabajo de diseño: no se programa ni se ejecuta nada. El objetivo es pasar el modelo 
de MongoDB del Avance 2 a tablas de SQL Server, para que en la entrega final solo

2.1 Diagrama y relaciones 
En docs/modelo-datos.md, sección «Diagrama»:

llaves foráneas. Puede hacerse con Mermaid, draw.io o una herramienta

● Para cada una de estas relaciones, una línea que diga su tipo (1 a muchos o

iniciativa, iniciativa–competencia, iniciativa–solicitud, proyecto–usuario y 
proyecto–iniciativa. Una relación 1 a muchos se resuelve con una llave foránea; 
una muchos a muchos, con una tabla intermedia.

● Una tabla «Del documento a la tabla»: para cada colección y cada arreglo del

2.2 Descripción de cada tabla 
En docs/modelo-datos.md, sección «Tablas»: una tabla por cada tabla de la base, 
con estas columnas. Ejemplo con la tabla Usuarios: 
Columna  | Tipo          | ¿Obligatoria? | Llave    | Regla 
Id       | INT IDENTITY  | Sí            | Primaria | 
Nombre   | NVARCHAR(80)  | Sí            |          | 
Correo   | NVARCHAR(120) | Sí            |          | UNIQUE (no se repite) 
Carrera  | NVARCHAR(60)  | No            |          | 
En las tablas que apuntan a otra, la columna de la llave foránea indica a qué tabla 
apunta (por ejemplo, PropietarioId → Usuarios) y qué pasa si se intenta borrar el 
registro al que apunta: se impide, se borra también o queda vacío. 
2.3 Plan de migración de MongoDB a SQL Server 
En docs/modelo-datos.md, sección «Plan de migración»: los pasos para pasar los 
datos del Innovation Hub de MongoDB a SQL Server, en orden. Para cada paso se 
entrega lo que se indica: 
● Paso 1 — Inventario. La lista de colecciones del Avance 2 con sus campos, 
indicando cuáles son arreglos embebidos y cuáles son referencias a otra 
colección. 
● Paso 2 — Correspondencia. Para cada colección, la tabla a la que pasa; para 
cada arreglo, la tabla hija o intermedia que lo reemplaza; para cada referencia, 
la llave foránea. Es la tabla «Del documento a la tabla» de la sección 2.1. 
● Paso 3 — Orden de creación de las tablas. Primero las que no apuntan a 
ninguna otra; después las que dependen de ellas. No se puede crear una llave 
foránea hacia una tabla que todavía no existe. Ejemplo: 
1. Usuarios, Competencias              (no dependen de nadie) 
2. UsuarioCompetencias, Iniciativas    (apuntan a Usuarios y Competencias) 
3. IniciativaCompetencias, Equipos     (apuntan a Iniciativas) 
4. Solicitudes, Proyectos              (apuntan a Iniciativas y Usuarios) 
● Paso 4 — Identificadores. En MongoDB cada documento tiene un _id 
ObjectId; en SQL Server cada fila tendrá un Id numérico. Explique cómo se 
mantienen las referencias al cambiar de uno a otro, por ejemplo con una tabla 
de equivalencias _id → Id. 
● Paso 5 — Carga de datos. Los datos de prueba, escritos como tablas y en el 
mismo orden del paso 3: al menos 3 usuarios, 5 competencias, 3 iniciativas 
con distintos niveles de visibilidad, 2 solicitudes y 1 proyecto, con sus 
relaciones (qué competencias tiene cada usuario, cuáles requiere cada 
iniciativa, quién está en cada equipo). 
● Paso 6 — Verificación. Cómo se comprueba que no se perdió nada: por 
ejemplo, contar las filas de cada tabla y compararlas con los documentos de 
cada colección.

2.4 Consultas SQL 
En docs/consultas.sql: al menos cinco consultas escritas a mano, cada una con un 
comentario que diga qué hace y qué resultado debería dar con los datos de prueba. 
No es obligatorio ejecutarlas. 
● Un JOIN entre dos tablas relacionadas 1 a muchos. Ejemplo: las iniciativas con 
el nombre de su propietario. 
● Un JOIN que recorra una relación muchos a muchos. Ejemplo: las 
competencias que requiere cada iniciativa. 
● Un conteo con GROUP BY. Ejemplo: cuántas solicitudes tiene cada iniciativa. 
● Un UPDATE y un DELETE, con su WHERE. 
● Un INSERT que la base debería rechazar por una llave o una restricción, y por 
qué. 
2.5 Diseño de dos rutas de lectura 
En docs/rutas.md: escoja dos rutas GET del contrato del Avance 2 que no requieran 
iniciar sesión; al menos una debe mostrar datos de una relación muchos a muchos. 
Para cada ruta, entregue: 
● La ruta y qué devuelve. Ejemplo: GET /api/initiatives/{id}, el detalle de una 
iniciativa. 
● Las tablas que necesita leer y la consulta SQL que obtiene esos datos. 
● El JSON que respondería, armado con los datos de prueba, con los mismos 
nombres de campo que responde hoy el servidor Express y los identificadores 
como texto.
